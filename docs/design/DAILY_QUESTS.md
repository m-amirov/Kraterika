# Ежедневные задания — дизайн v0.2

**Статус:** `DESIGN_ONLY / OWNER_REVIEW_PENDING`. Не реализовано в игре. Сюжет, сооружения, энергия и доступ к главам **никогда не зависят** от ежедневного входа. Система предназначена для короткого возвращения на 5–10 минут без таймерного гринда, streak-штрафов, рекламы и платных пропусков.

## Что видит игрок

В левой/верхней части общей карты — карточка **«Задания дня»** с тремя понятными целями: обычная поставка, инженерное действие, инженерное мастерство. Каждая карточка имеет цель, счетчик, возможность перейти к подходящему уже открытому контракту и явно указанное время следующего обновления.

Первый доступ после `CT-02`, чтобы новичка не отвлекать до освоения двух роботов и управления. Если игрок не приходил вчера, он **ничего не теряет**: никаких обязательных серий входов и блокировки будущего дня.

### Подбор доступных заданий

- В каждый календарный день UTC выбрать **ровно три задания**: по одному из `basic / engineering / mastery`. Состав по одной категории для каждого игрока зависит от **открытых механик** и набора законченных контрактов, чтобы не требовать ещё закрытой зарядки/крана.
- Источник выбора — версионированный реестр [DAILY_QUESTS_REGISTRY.json](DAILY_QUESTS_REGISTRY.json). Выбор детерминирован по `UTC-date + stable eligibility tier + rotation version`; выбранный набор хранится в прогрессе и **не переопределяется посреди дня**, если игрок открыл новую главу.
- Если нет доступного улучшения медали (везде золотые), `DQ-BEST` исключается. Если игрок не достиг главы 3, не выбирать задания на ограничения мощности. Не требовать открытия новых основных контрактов сегодня.
- Действия считаются только по **событиям, подтверждённым успешным завершением операции**. Не засчитывать многократное переключение стрелки в пустой попытке, клики по строению, холостой запуск, многократное обновление страницы. Счетчик груза считает **уникальные delivery event IDs** в зафиксированных успешных попытках; replay может засчитаться в дневную активность, но не выдаёт first-clear материалы.
- После 00:00 UTC новая тройка появляется при следующей проверке доверенного времени; старые невостребованные задачи завершены. При смене дня **посреди операции** событие привязано к UTC-дате **успешного commit**; недоступная устаревшая карточка не награждается.
- Без доступного серверного времени сохраняется кампания и текущая попытка, но новые daily и конкурентные награды **не выдаются по местному Date.now()**. В режиме локального тестирования применяется явно обозначенный deterministic mock time.

В реестре предусмотрены fallback для всех трех категорий. При невозможности выполнить карту-условие игроку предлагается **явно заменить одну несовместимую карточку**, не заставляя входить ежедневно. Замена не должна работать как бесконечная генерация лёгких задач; максимум одна техническая переоценка по причине `UNREACHABLE`, с записью причины в state.

## Награда: не ломаем экономику

- За отдельные карточки начисляется прогресс коллекции **«Лунный журнал»**; это не ещё одна расходуемая валюта и **не материалы для обязательных зданий**.
- Выполнил **не менее 2 из 3** карточек одного UTC-дня — получил **один дневной штамп**, максимум 1 за дату.
- Совокупные уникальные даты с полученным штампом открывают косметические награды на **3 / 7 / 14 / 30** разных днях: световой маячок, окраску транспортной площадки, декоративные растения для купола, памятный модуль станции (точные арты — Art Production backlog).
- Награды не влияют на скорость, количество энергии, медали или лидерборды и не дают pay-to-win. Незакрытый день ничего не отнимает; шкала суммирует **любые** дни, не серию подряд.

## Время, сохранения и конфликты

- Яндекс Игры документируют `ysdk.serverTime()` (миллисекунды) как механизм времени для daily events; day key = `new Date(serverMs).toISOString().slice(0,10)` (UTC). Сбрасывать по календарной UTC-дате, а не через 24 ч после входа и не по системным часам браузера.
- Хранить `daily.rotationVersion`, `dayKey`, `questIds[3]`, `progressEventIds` (bounded), `claimedQuestIds`, `stampedDayKeys`, `cosmeticsUnlocked` и последний надёжный server time. Сохранять сразу после подтверждённого события.
- На двух устройствах объединять `claimedQuestIds` и `stampedDayKeys` по set-union и пересчитывать общее количество штампов **по уникальным датам**. Внутридневные счетчики восстанавливать по уникальным event IDs; если нет надёжного reconciliation — помечать `SYNC_CONFLICT` без выдачи лишнего.
- `player.setData` не делает произвольные клиентские операции атомарными между устройствами. Без серверной валидации нельзя **гарантировать** полное исключение подделки времени/событий/сохранения: не связывать с ними деньги или соревновательные преимущества.
- Гость выполняет ежедневные задачи локально без авторизации, но при отсутствии SDK-доверенного времени новые серверно-дневные награды не активируются. После авторизации — cloud merge, не затирать гостевой прогресс пустым облаком.

## Источники и реальные gate

- [Yandex Server Time](https://yandex.ru/dev/games/doc/ru/sdk/sdk-server-time) — `ysdk.serverTime()` и календарный UTC reset.
- [Yandex Player data](https://yandex.ru/dev/games/doc/ru/sdk/sdk-player) — `getData/setData`, облачный лимит 200 КБ и частотные ограничения.

**Проверки для реализации:** симулировать границы 23:59:59/00:00:00 UTC, смену региона, смену системного времени, 2 устройства, offline, успешный и отменённый контракт, доставку одного груза в 2 разных attempt, повтор одного события, разные версии шаблона, 0/1/2/3 готовых задания и claim дважды. Только после реальной интеграции SDK и UI допускается `DAILY_RUNTIME_VERIFIED`.
